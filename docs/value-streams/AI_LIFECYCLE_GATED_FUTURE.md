# AI capability lifecycle — gated future architecture

The AI capability lifecycle is modelled so the organisation knows what it would require. It is
**not implemented, not enabled, and not partially available**.

## Current state

- Operating status: `gated-future`
- Authority: `gated-future`
- Implementation status: `not-implemented`
- Available gate dispositions: **blocked** and **refused** only. There is no pass option.

No AI feature exists in this system. No model is called. No inference runs. No content in this
repository is produced by a runtime AI capability.

## What the trigger gate would require before any AI capability advances

1. A named human accountable for every AI-assisted output.
2. Evidence binding each output to the specific inputs and version that produced it.
3. A review step performed by a function independent of the one requesting the capability.
4. A refusal path that is easier to take than acceptance.
5. A stated failure model: what the capability gets wrong, how often, and who is harmed.
6. Data handling cleared under the live-personal-data gate, which is itself closed.
7. No autonomous high-impact decision, at any confidence level.
8. A withdrawal path that removes the capability without removing the record of its use.

## Reading rule

Any surface displaying this stream must mark it as target-state architecture. Displaying it
without that marker would be a claim the system does not hold.
